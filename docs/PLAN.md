# 우리팀 기획안

## 1. 프로젝트 개요

- **프로젝트명**: 우리팀 (wooriteam)
- **한 줄 소개**: 대학생·비전공자를 위한 역할 중심 팀 프로젝트 구인 플랫폼
- **기획 배경**: 팀 프로젝트 구인 시 에브리타임·오픈카톡 등 비공식 채널에 의존하는 문제에서 출발. 역할별 모집공고를 체계적으로 게시·지원할 수 있는 전용 서비스의 필요성 확인.
- **목표**: MVP 1개월 내 개발 완료 및 배포. 대학생·비전공자 타겟으로 진입 장벽을 낮춘 구인·지원 흐름 구현.

## 2. 문제 정의

- **구인 채널 분산**: 에브리타임, 오픈카톡방, 디스코드 등 채널이 파편화되어 원하는 역할을 모집하는 팀을 찾기 어렵다.
- **역할 기반 탐색 불가**: 기존 서비스는 공고가 프로젝트 단위로 올라와, 특정 역할(백엔드·프론트엔드 등)만 필터링해 보기 어렵다.
- **높은 진입 장벽**: 기존 유사 플랫폼의 공고 대부분이 현업자·경력자 중심의 분위기를 띠어 대학생·비전공자가 지원을 망설이게 된다.

## 3. 타겟 사용자

- 포트폴리오용 프로젝트를 찾는 대학생
- 부트캠프 수료 후 협업 경험을 원하는 비전공자
- 졸업작품·해커톤·사이드프로젝트 팀원을 모집하려는 학생 기획자
- 소규모 초기 팀 구성이 필요한 팀 리더

## 4. 서비스 시나리오

### 시나리오 A — 팀원 모집
1. 회원 가입 후 모집 공고 작성
2. 모집 역할 선택 (백엔드/프론트엔드/디자인/기획 중 복수 선택)
3. 프로젝트 소개, 역할별 할 일·기술스택, 난이도, 프로젝트 유형 입력
4. 선택한 역할의 탭 각각에 공고 노출
5. 지원자 목록 확인 후 연락처로 직접 컨택

### 시나리오 B — 팀 합류
1. 비회원도 역할 탭에서 공고 열람 가능
2. 원하는 공고의 지원 폼 제출 (지원동기, 기술스택, 경험, 연락처)
3. 게시자가 지원자 정보 확인 후 연락

### 시나리오 C — 회원 프로필 공개 (Should)
1. 회원이 프로필 공개 설정 시 기술스택·경험·이메일 공개
2. 구인자가 프로필 목록에서 직접 컨택 가능

## 5. 핵심 기능

- 역할 탭 분류
- 모집공고 CRUD
- 역할별 지원 기능
- 회원 기능

## 6. MVP 정의

### Must
- **역할 탭 분류**
  - 백엔드 / 프론트엔드 / 디자인 / 기획
  - 하나의 공고가 여러 탭에 동시 노출 가능
- **모집공고 CRUD**
  - 공고 작성
  - 탭별 공고 목록 및 상세 조회
  - 공고 수정 및 삭제
  - 공고 마감 처리 (수동 모집 완료 처리 및 마감된 공고를 탭에서 필터링)
- **모집공고 지원**
  - 지원 폼 제출
  - 공고 게시자만 지원자 목록 및 정보 확인 가능
- **회원 기능**
  - 회원 가입 / 로그인 / 로그아웃 / 회원탈퇴
  - 본인이 게시한 모집 공고 목록 확인
  - 본인이 지원한 모집 공고 목록 확인

### Should
- **게시자 필터링**
  - 게시자가 난이도, 기술 스택, 모집 유형 등을 직접 설정
- **회원 프로필 공개**
  - 기술 스택, 경험, 이메일 등을 공개 설정
  - 공개 시 구인 중인 유저가 직접 컨택 가능
  - 회원들에게만 프로필이 공개되고 공개된 프로필을 확인 가능
- **검색 기능**
  - 관심 있는 프로젝트 또는 소속 검색
  - 프로젝트 제목 및 내용 중에서 검색 가능

### Could
- **지원자 필터링**
  - 필터링된 모집 조건을 지원자가 공고 목록 확인 시 필터링해서 열람
- **공고 자동 마감**
  - 마감일 설정 시 자동으로 공고 마감
- **공고 북마크**
  - 관심 공고 저장
- **신고/스팸 처리**
- **그룹 기능**
  - 소속 그룹을 생성하고 만들어진 그룹 중에서 가입 신청 가능
  - 그룹 내에서만 모집 공고 게시
  - 특정 단체 소속 혹은 대학교 소속 단위로만 모집할 수 있게 함

## 7. ERD

| 엔티티 | 주요 컬럼 | 설명 |
|---|---|---|
| User | id, email, password, nickname, created_at | 회원 정보 |
| UserProfile | user_id, tech_stack, experience, is_public | 프로필 공개 정보 (Should) |
| Post | id, user_id, group_id, title, description, difficulty, project_type, is_closed, deadline, created_at | 모집공고. group_id(nullable)·deadline(nullable)은 Could |
| PostRole | id, post_id, role_type, description, tech_stack | 공고별 모집 역할 (Post 1:N) |
| Application | id, post_id, role_id, user_id, motivation, tech_stack, experience, contact, created_at | 지원 정보 |
| Group | id, owner_id, name, description, created_at | 소속 그룹 (Could) |
| GroupMember | id, group_id, user_id, status, joined_at | 그룹 멤버·가입 신청. status ENUM: PENDING·APPROVED (Could) |
| Bookmark | id, user_id, post_id, created_at | 관심 공고 북마크 (Could) |
| Report | id, reporter_id, target_type, target_id, reason, created_at | 신고/스팸. target_type ENUM: POST·USER (Could) |

## 8. 화면 구성

- **메인 페이지**: 서비스 소개, 역할 탭 진입 버튼, 검색창 (Should)
- **회원가입/로그인**: 이메일·비밀번호 기반 인증
- **역할 탭별 페이지**: 백엔드/프론트엔드/디자인/기획 탭 구분, 공고 카드 리스트, 그룹 소속 공고 필터 (Could)
- **검색 결과 페이지**: 검색어에 매칭된 공고 목록 (Should)
- **공고 상세**: 프로젝트 소개, 역할별 할 일·기술스택, 지원 버튼
- **공고 작성/수정**: 프로젝트 정보 입력, 역할 복수 선택, 역할별 상세 입력, 그룹 선택 옵션 (Could)
- **지원 폼**: 지원 역할 선택, 지원동기·기술스택·경험·연락처 입력
- **마이페이지**: 내가 쓴 공고 목록 (마감 처리 버튼), 내가 지원한 공고 목록, 프로필 편집 (기술스택·경험 입력, 공개 여부 토글) (Should), 북마크 목록 (Could)
- **지원자 목록**: 게시자 전용. 역할별 지원자 카드 (지원동기·기술스택·연락처)
- **회원 프로필 목록**: 공개 설정된 회원 카드 리스트, 기술스택·경험 요약 (Should)
- **회원 프로필 상세**: 기술스택·경험·이메일, 컨택 버튼 (Should)
- **그룹 목록**: 가입 가능한 그룹 카드 리스트, 가입 신청 버튼 (Could)
- **그룹 상세**: 그룹 정보·멤버 목록·해당 그룹 공고 목록, 가입 신청 관리 (그룹장 전용) (Could)
- **그룹 생성**: 그룹명·설명 입력 (Could)

## 9. 마일스톤

### 1단계) 설계 & 로컬 MVP 개발

**목표**: 기술 명세 확정 및 로컬 환경에서 Must 기능 동작 확인

1. 도메인 및 데이터 모델 설계
    - User, Post, PostRole, Application 등 엔티티 확정. ERD 완성 및 엔티티 설계 요약 작성
2. 핵심 API 명세
    - 회원 인증, 공고 CRUD, 지원 등 핵심 API의 Method, URL, Request/Response 표 완성
3. 로컬 개발 환경 구축
    - MySQL 로컬 설치 및 DB 생성. application.yaml 및 .env 설정. `./gradlew bootRun`으로 실행 확인
4. Must 기능 백엔드 구현
    - 회원 가입/로그인/로그아웃/탈퇴 (JWT 인증)
    - 모집공고 CRUD 및 마감 처리
    - 역할별 지원 폼 제출 및 지원자 목록 조회 (게시자 전용)
5. Must 기능 프론트엔드 구현
    - 역할 탭별 공고 목록, 공고 상세, 공고 작성/수정, 지원 폼, 마이페이지
6. 로컬 E2E 검증 및 문서화
    - Must 기능 전체 API 동작 및 DB 저장 확인. 로컬 실행 방법 가이드 작성

### 2단계) 클라우드 인프라 구축 및 CI/CD

**목표**: Terraform으로 AWS 인프라를 구축하고 GitHub Actions CI/CD 파이프라인을 통한 자동 배포 완성

1. 네트워크/보안 설계 확정
    - VPC CIDR, 서브넷(Public/Private), Security Group (ALB→ECS→RDS) 설계 완료. ECS Task Role 정의
2. 인프라 IaC 구축 (Terraform)
    - VPC, 서브넷, IGW, ALB, ECS Fargate 클러스터, RDS, Secrets Manager IaC 코드 작성 및 배포
3. DB 및 보안 설정
    - RDS MySQL 구성. Secrets Manager에 DB 자격증명·JWT 시크릿 등록. 초기 스키마 마이그레이션
4. CI 파이프라인 구축
    - GitHub Actions: 코드 빌드, 단위 테스트, ECR 이미지 빌드·푸시 자동화
5. CD 파이프라인 구축
    - ECR 이미지를 ECS Fargate 서비스에 자동 배포하는 파이프라인 구성
6. 클라우드 E2E 검증
    - CI/CD로 배포된 서비스에서 Must 기능 전체 동작 최종 검증

### 3단계) Should 기능 구현

**목표**: 게시자 필터링, 회원 프로필 공개, 검색 기능 구현으로 서비스 완성도 향상

1. 게시자 필터링 구현
    - 공고 작성 시 난이도·기술 스택·모집 유형 설정 및 필터링 API·UI 구현
2. 회원 프로필 공개 구현
    - UserProfile 엔티티 및 공개 설정 API 구현. 회원 프로필 목록·상세 화면 구현
3. 검색 기능 구현
    - 공고 제목·내용 기반 검색 API 구현. 메인 페이지 검색창 및 검색 결과 페이지 구현
4. Should 기능 통합 E2E 검증

### 4단계) Could 기능, 안정화 및 운영 준비

**목표**: Could 기능 구현 및 서비스 품질 최종 검증, 운영 대비

1. Could 기능 구현
    - 공고 자동 마감 (deadline 기반 스케줄러)
    - 공고 북마크
    - 그룹 기능 (그룹 생성·가입 신청·그룹 공고 필터)
    - 신고/스팸 처리
2. 성능 테스트
    - 주요 API 응답 속도 측정 및 병목 구간 (DB 쿼리, 인덱스) 분석
3. 모니터링 설정
    - CloudWatch 로그·메트릭 대시보드 구축. 주요 장애 시나리오 Runbook 작성
4. 리팩터링 및 비용 최적화
    - 불필요 코드·인프라 정리. RDS 인스턴스 사이징 및 비용 효율성 점검
5. 문서화 및 발표 준비
    - 전체 산출물 통합 및 최종 발표 자료 작성

## 10. 기술 스택

| 영역 | 기술 | 선택 이유 |
|---|---|---|
| Backend | Spring Boot (Java), Spring Security + JWT | 기존 프로젝트 경험 활용 |
| Frontend | React + TypeScript, Vite | 컴포넌트 기반 탭 UI 구현에 적합 |
| Database | MySQL (RDS) | 관계형 구조 (공고-역할-지원 1:N) |
| Infra | AWS ECS Fargate, ALB, RDS, Secrets Manager, ECR | CI/CD 고도화 |
| IaC | Terraform | AWS 인프라 코드화 |
| CI/CD | GitHub Actions | 빌드·배포 자동화 |

## 11. 기대 효과

- 역할 탭으로 원하는 포지션의 공고만 빠르게 탐색 가능
- 난이도·프로젝트유형 태그로 본인 수준에 맞는 팀을 찾는 심리적 부담 감소
- 지원자 연락처가 게시자에게만 공개되어 개인정보 노출 최소화
